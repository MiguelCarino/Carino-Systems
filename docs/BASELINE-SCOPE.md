# Fleet baseline — scope

Status: **built 2026-10-20** except §3.7 (browser measurements) and item 20 (skipped). Live status: `baseline/REPORT.md`.

Two goals, one rule.

1. **Baseline.** Every carino.systems site gets the same short list of
   housekeeping items (legal pages, HTTPS, search metadata, 404, …).
2. **Provenance.** Every repo says, file by file, what a person has read and
   what is still 100 % AI-written and unreviewed.
3. **Rule: systematically simple.** Each item is done *one way*, by *one
   script*, from *one source of data*. Nothing is hand-copied into 42 sites.
   When you study the code later, there is one place to look per item.

## 2. The pieces (all new code lives in `Carino-Systems/baseline/`)

```
Carino-Systems/
  baseline/
    sites.json        the one list of all 42 sites (repo, folder, domain, kind)
    check.py          read-only: runs the 20 checks, prints a table, exits 1 on a FAIL
    apply.py          writes the generated files; shows a diff; --write to save
    templates/        404.html, robots.txt, head block — plain files, no templating engine
    REPORT.md         check.py's last output, committed, so status is visible in git
  legal.html          §3.5
  propagate.sh        unchanged in this scope
```

Why this shape:

- **`sites.json` is new because nothing lists all 42 today.** `tools.json`
  is the hub's *display* registry. It lacks the hub itself, dlss, test,
  jellyfish and butter, and it lists MultiWeb, which is not a site.
  `sites.json` says what exists; `tools.json` keeps saying what to show.
  Descriptions are read from `tools.json` by name, not copied.
- **`check.py` is the audit from this session, kept.** Every item states its
  method in one sentence at the top of its function. A ✓ always means "the
  script verified it", never "someone said so".
- **Generated files carry a marker line**
  (`<!-- generated by Carino-Systems/baseline/apply.py — edit the template, not this file -->`).
  When reading a site, a marked file says where its source is.
- **Python standard library only.** No packages, matching Law's
  `validate.py` and Branding's `marks.py`.
- **`propagate.sh` is left alone.** It already has five canonical sources in
  four repos. Folding it in would be a cleanup of its own (§6), not part of
  this scope.

## 3. Work, in order

Each step ends with `check.py` green for that item before the next starts.

### 3.1 HTTPS — repo settings, no code (item 4)

- Turn on "Enforce HTTPS" for the 16 sites
  (`gh api -X PUT repos/MiguelCarino/<repo>/pages -F https_enforced=true`).
- hardware and learn: remove and re-add the custom domain in Pages settings
  so GitHub issues the certificate. Enforce once it shows "approved".
- jellyfish: add the DNS record by hand at the DNS host:
  `CNAME  jellyfish  →  miguelcarino.github.io`, the same as every other
  subdomain. Then re-save the custom domain in the repo's Pages settings
  so GitHub issues the certificate, and enforce HTTPS.
- `check.py` verifies with a live `http://` request expecting 301 → https.

### 3.2 robots.txt, sitemap.xml, 404.html — generated (items 7, 15)

- **robots.txt:** one template for every site, `Allow: /` plus
  `Sitemap: https://<domain>/sitemap.xml`. The hub's current file allows
  only `/` and assets, has a dead `BadBot` block and a crawl-delay; it is
  replaced by the same template.
- **sitemap.xml:** per site it lists the root URL only, since every tool is
  one page with hash routes. The hub's sitemap additionally lists the 42
  domains.
- **404.html:** one static page in the shared gold-C style, with "this page
  does not exist" in the five fleet languages and a link to the site root
  and the hub. No scripts, so it cannot break.

### 3.3 Head block — generated (items 5, 6)

One marked block in each `index.html` `<head>`:

```html
<!-- carino:head — generated by Carino-Systems/baseline/apply.py -->
<meta name="description" content="… from tools.json desc …">
<link rel="canonical" href="https://<domain>/">
<meta property="og:title" …> <meta property="og:description" …> <meta property="og:url" …>
<script type="application/ld+json">{"@type":"WebApplication", name, url, description, author: Carino Systems}</script>
<!-- /carino:head -->
```

- `apply.py` only ever replaces text *between* the two markers.
- Sites that already have a hand-written description or Open Graph tags
  have them moved inside the block once, so there is a single copy.
- The hub's JSON-LD is `Organization`, not `WebApplication`.
- ButterEye's block omits Carino as author (see §5).

### 3.4 Provenance ledger — every repo (the second goal)

See §5. It comes before the content steps on purpose: every file those
steps touch is logged from the start.

### 3.5 Legal page — one page on the hub (items 1, 2, 3)

- `carino.systems/legal.html` has three sections: **Legal notice**
  (who runs the sites, contact, licence), **Privacy** (no accounts, no
  tracking, files never leave the browser, the per-site exceptions:
  Stocks/Currency call price APIs, CVE calls NVD, Ping probes hosts,
  Topo share links), and **Cookies and storage** (the one language cookie
  plus localStorage settings, with what each is for).
- **One page, not 42.** Every site links to it. Sites on the shared navbar
  (propagate.sh's GROUPA) get the link by one edit to `CVE/carino-navbar.js`
  and a propagate run. Sites with their own navbar (BESPOKE, the hub,
  ButterEye, dlss, CyberCity, findmeadistro, Teleprompter) get it by hand, and
  `check.py` verifies all 42.
- **Found while scoping:** Ping, Offline, Law, Stocks, Jellyfish and Test load
  `carino-navbar.js` but are not in GROUPA, so propagate.sh never updates
  their copy. Offline, Law and Jellyfish match the canonical file and can
  join GROUPA as they are. Ping, Stocks and Test carry local edits (Ping's
  slimmed navbar, for one), so each is either folded back into the canonical
  file or recorded as a deliberate fork, never silently overwritten.
  `check.py` then flags any site whose shared file differs from the
  canonical one without being recorded.
- Spanish and English text, plus the usual es / pt-BR / ja / ru for the
  page chrome.
- **Text: `legal.html`** (Spanish governs, English translation; reviewer questions in `docs/LEGAL-REVIEW.md`),
  drafted by AI from facts in the code: the `carino_lang` cookie and each
  outside service each tool calls. It is marked "Redactado por IA · Drafted
  by AI" and stays `ai` in the ledger until a person, ideally a Mexican
  lawyer for the LFPDPPP privacy notice, has reviewed it. The published
  page shows that status at the top.

### 3.6 Content fixes — by hand, small (items 10, 11)

- Add the missing `alt` text (distro first).
- Convert distro's 308 KB PNG to WebP.
- `check.py` then fails on any new `<img>` without `alt`, or on any served
  image over 300 KB. Doc screenshots outside the served pages are exempt.

### 3.7 Measured checks — Playwright, one site at a time (items 12, 13, 14, 16)

- `check.py --browser` loads each site in headless Chromium, sequentially
  with one browser, to keep memory use low. It:
  - records transfer size and load time;
  - computes text/background contrast for visible text (WCAG AA 4.5:1);
  - screenshots at 390 px and flags horizontal page scroll;
  - HEADs every external link once.
- Results go to `REPORT.md`. These checks report; they do not fail the
  build until the first full pass is clean.

## 4. Decisions

Decided 2026-10-19:

1. **Analytics (19): none, deliberately.** The report marks the item
   "deliberately not installed", and the legal page says so. `check.py`
   turns it into a guard: it fails if a known tracker (Google Analytics/Tag
   Manager, Plausible, Umami, GoatCounter, Clarity, Cloudflare Insights,
   Meta pixel) ever appears in a site.
2. **WhatsApp (18): none.** No new contact button anywhere. The navbar's
   GitHub and LinkedIn links remain the only contact, including on the
   legal page.
3. **Google Business Profile (8): none.** Reported as deliberately absent.
4. **jellyfish: add the DNS record** (§3.1).
5. **Legal text: drafted by AI, marked as such.** The draft is
   `legal.html`. It carries a "Redactado por IA · Drafted by AI"
   notice at the top of the document and of the published page, is `ai`
   in `AUDIT.md`, and lists what a person and a lawyer must confirm.
6. **No cookie banner.** It follows from 1: the only cookie is the language
   preference, and storage is functional.

### Still open: item 20, "a single call to action"

**What the item means.** It is a rule from marketing sites. Each page
should have *one* thing you most want the visitor to do, such as "Book a
call", "Buy" or "Message us". That one thing gets the one prominent button.
Everything else on the page is quieter, so the visitor never has to choose
between several buttons that all shout. A page with "Call us", "WhatsApp",
"Subscribe", "See plans" and "Download brochure", all equally loud, fails
it.

**Why it barely applies to the tools.** A tool page's action is using the
tool: drop a file, press Start, type a host. That is already the only
loud control. A checklist written for a business card site expects a
sales button, and the decisions above rule that out.

**Where it does apply: the hub.** carino.systems has one job, getting a
visitor to open a tool. Today the page offers several routes of similar
weight: the hero, the cycling spotlight, the wall of 35 plates, the six
safety cards, and the navbar's GitHub/LinkedIn icons.

**The check, if adopted, is a design review, not a script:**

- one primary button style per page, used once ("Open <tool>" in the
  spotlight, or the wall itself);
- everything else in secondary or link style.

**Options:**

- **(a)** Review the hub only and keep its single primary action
  ("open a tool").
- **(b)** Also check each tool's landing state, so that before a file is
  loaded exactly one control is primary.
- **(c)** Drop the item as not applicable.

**Recommendation: (a)**, with (b) folded into the mobile screenshots of
§3.7 at no extra cost.

## 5. Provenance — "what has been audited, what is 100 % AI"

### The problem

Git cannot answer this. Every commit is authored as Miguel, and by fleet
rule commits carry no AI attribution, so the history looks hand-written
when most of it is not. The record has to be explicit and separate.

### The ledger: `AUDIT.md` in every repo root

```markdown
# Audit ledger

Default: every file not listed below is **ai** — written by AI, not yet read by a person.

| File | Status | By | Date | At commit | Notes |
|---|---|---|---|---|---|
| js/parse.js | reviewed | Miguel | 2026-11-02 | 7bbc244 | read fully; tested against own logs |
| js/stats.js | ai | | | | |
| index.html | human | Miguel | | | written by hand |
```

Three statuses, no others:

- **`ai`** — written by AI; no person has read it. This is the default for
  everything, including files from before this scope. When unsure, it is
  `ai`.
- **`reviewed`** — a person read the whole file at the named commit.
- **`human`** — a person wrote it.

### How it stays honest

- **`check.py --provenance`** compares each `reviewed` file with its
  recorded commit. If the file changed since, it shows **`reviewed →
  stale`**. A review covers the code that was read, not later edits.
  Nothing marks itself reviewed: only Miguel edits the Status column.
- Generated files (§3.2–3.3) and vendored libraries get their own rows,
  `generated` or `vendored` in Notes, pointing to their source, so they are
  not mistaken for code to study.
- From now on, when AI writes or changes a file, that file's row is set to
  `ai` in the same commit. Changing a `reviewed` file makes it stale
  automatically, so nothing needs to be remembered.

### Where it shows

- `REPORT.md` gets a provenance column per site, for example
  "Ping — 3 of 14 files reviewed".
- The legal page carries one honest sentence: *"Most of the code on these
  sites was written with AI assistance. Each repository's `AUDIT.md` lists
  which files a person has reviewed."* It is linked to the repos.

### A study order, as a by-product

`check.py --provenance --study` lists the unreviewed files fleet-wide,
**shared files first**:

1. the files `propagate.sh` copies: navbar, clock, lang, bridge, diag;
2. the baseline scripts;
3. per site, the smallest files first.

Reading the shared files once covers them in every site, so the reviewed
count rises fastest that way.

### ButterEye

It is not a Carino product. It gets the technical items (HTTPS, robots,
sitemap, 404, ledger), but no link to the Carino legal page and no Carino
author in its metadata. Its own docs already carry its licence.
